## 1. Обзор и постановка проблемы

### 1.1. Что мы строим и зачем
Мы строим веб-сервис, который по четырём характеристикам квартиры (площадь, количество комнат, этаж, этажность дома) предсказывает её рыночную стоимость в рублях.
Пользователь вводит параметры в веб-форме или отправляет запрос в REST API и получает оценку цены.
Данные собираются с сайта объявлений о продаже квартир (Instant Data Scraper), обрабатываются скриптом `preprocess.py`, модель обучается скриптом `train.py` и подключается к Flask-сервису.

**Бизнес-цель (учебная):** Отработать полный цикл MLOps-зрелости: от анализа данных и трекинга экспериментов до контейнеризации, мониторинга и CI/CD.

### 1.2. Почему это важно сейчас
Проект является базой для выполнения семинарских заданий. Без работающего дизайн-документа невозможно осмысленно внедрять DVC, MLflow и мониторинг, так как непонятно, какие артефакты и метрики отслеживать.

## 2. Цели и границы проекта

### 2.1. Цели (In-Scope)
1.  Реализовать REST API на Flask для инференса модели.
2.  Обеспечить возможность переключения между моделями (baseline и улучшенная) через переменные окружения или аргументы запуска.
3.  Настроить воспроизводимость данных (DVC) и экспериментов (MLflow).
4.  Развернуть базовый мониторинг (дашборд) и CI/CD пайплайн.

### 2.2. Не-цели (Out-of-Scope)
1.  **Высокая точность предсказания:** Мы не стремимся побить рекорд на Kaggle. Модель нужна как «заглушка» для демонстрации инфраструктуры.
2.  **Сложный парсинг и Feature Engineering:** Входные признаки жестко заданы (4 числовых признака). Использование текстовых описаний или изображений не предусмотрено.
3.  **Продакшен-нагрузка:** Сервис не рассчитан на высокий RPS, не требуется отказоустойчивость уровня 99.99%.

## 3. Данные и метрики

### 3.1. Данные
Используется табличный датасет с характеристиками жилья, собранный из объявлений о продаже квартир (выгрузка в Excel через Instant Data Scraper, затем `preprocess.py` → `features/all_features.csv`). Дубликаты объявлений удаляются по `id`.

**Признаки:**

| Признак | Тип | Описание |
|---|---|---|
| `area` (`total_meters`) | float | Общая площадь квартиры, м² |
| `rooms` | int | Количество комнат (0 — студия). В модель подаётся как one-hot: `rooms_1`, `rooms_2`, `rooms_3` |
| `floor` | int | Этаж квартиры. В модель подаётся как флаги `first_floor` (первый этаж) и `last_floor` (последний этаж) |
| `total_floors` (`floors_count`) | int | Количество этажей в доме |

**Целевая переменная:** `price` — цена квартиры в рублях (int).

**Риски данных (Data Leakage):** При разделении выборки необходимо следить, чтобы объекты из одного дома (одинаковый `total_floors` и адрес, если появится) не попадали одновременно в train и test, иначе метрики будут завышены.

### 3.2. Метрики качества модели
*   **Основная метрика:** **MAE (Mean Absolute Error)**. Почему: Для бизнеса (покупателя/продавца) важна абсолютная ошибка в рублях, а не относительная. MAE интерпретируется легче, чем RMSE.
*   **Дополнительная метрика:** **MAPE** (для понимания процента отклонения).
*   **Baseline:** `baseline_const` (константное предсказание медианной цены). Любая ML-модель обязана побить этот baseline на отложенной выборке, иначе ее внедрение не имеет смысла.

## 4. Архитектура и инфраструктура

### 4.1. Высокоуровневая схема
![](img/arch.png)

**Компоненты:**
*   **UI** (`service/templates/index.html`) — веб-форма в браузере, отправляет данные в API через `fetch`.
*   **Flask app** (`service/app.py`) — отдаёт страницу `/` и обрабатывает запросы к `/api/numbers`; авторизация по Bearer-токену (`APP_TOKEN`), CORS.
*   **Модели** (`service/predict.py`) — реестр моделей `MODELS`; модель выбирается через `MODEL_NAME` в `.env` или аргумент `-m`, также можно загрузить обученную `.pkl`-модель.
*   **Model storage** — хранилище сериализованных моделей (локальная папка, далее MLflow Model Registry).
*   **Logs** — логи запросов и ошибок в консоль и файл `service/flask.log`.
*   **Данные** — версионируются через DVC (`data.dvc`, удалённое хранилище S3).

### 4.2. Инференс
*   **Endpoints:**
    *   `GET /` — веб-страница с формой.
    *   `POST /api/numbers` — предсказание цены. Требует заголовок `Authorization: Bearer <APP_TOKEN>`.
        Тело запроса (JSON):
        ```json
        {"area": 45.5, "rooms": 2, "floor": 3, "total_floors": 9}
        ```

*   **Формат ответа:** JSON.
    *   Успех: `{"status": "success", "data": 10000000}` — предсказанная цена в рублях.
    *   Ошибка разбора входных данных: `{"status": "error", "data": "Ошибка парсинга данных"}`.
    *   Модель не реализована: код 501, `{"status": "error", "data": "<текст ошибки>"}`.
    *   Неверный токен: код 401.

## 5. Экспериментирование и валидация

### 5.1. Трекинг (MLflow)
Каждый запуск обучения логирует:
*   Параметры модели (гиперпараметры).
*   Метрики (MAE, MAPE на train/val).
*   Артефакт модели (сериализованный файл).
*   Хэш коммита и версию данных (DVC hash).

### 5.2. Схема валидации
Используется **K-Fold Cross-Validation** (K=5) на train-части и отдельный **Holdout set** (20%) для финальной проверки перед регистрацией модели в реестре.

## 6. Внедрение и мониторинг

### 6.1. CI/CD (GitHub Actions)
При пуше в ветку `main`:
1.  Запуск линтера (`flake8`).
2.  Запуск юнит-тестов (проверка, что API возвращает 200 и число).
3.  Сборка Docker-образа (опционально, если требуется в семинаре).

### 6.2. Мониторинг (Дашборд)
Поскольку сервис учебный, мониторим **технические метрики** и **дрифт данных**:
*   **Latency (p95):** Время ответа API.
*   **Error Rate:** Доля 5xx ошибок.
*   **Data Drift:** Сравнение распределения входных признаков (площадь, комнаты) с тренировочным датасетом. Если средняя площадь в запросах резко падает или растет, это сигнал, что модель работает не в тех условиях.

## 7. Риски и компромиссы

| Риск / компромисс | Последствие | Как снижаем |
|---|---|---|
| Мало признаков (всего 4, нет района, адреса, года постройки) | Низкая точность модели | Осознанный компромисс ради простоты; цель курса — инфраструктура, а не точность |
| Данные из одного источника и за короткий период | Модель устаревает при изменении рынка, смещение выборки | Регулярно пересобираем данные, версионируем их в DVC, следим за дрифтом |
| Ошибки парсинга объявлений (регулярные выражения) | Пропуски и выбросы в данных | Проверка пропусков, удаление дубликатов и выбросов в `preprocess.py` |
| Простая авторизация одним токеном | Низкая защищённость API | Достаточно для учебного проекта; токен хранится в `.env`, не в репозитории |
| Константный baseline в качестве модели по умолчанию | Сервис отдаёт одинаковую цену | Заменяем на обученную модель после семинара по MLflow |
| Flask dev-сервер | Не подходит для нагрузки | Для учебных целей достаточно; при необходимости — gunicorn + Docker |

## 8. Открытые вопросы 
1.  Нужно ли в рамках семинара по CI/CD деплоить сервис в облако (например, Render/Heroku) или достаточно локального запуска через Docker Compose?  
Ответ: Достаточно локального запуска через Docker Compose: сервис учебный, нагрузки нет, а облачный деплой добавит затраты и настройку секретов. Облако можно добавить позже как опцию.  
2.  Какой конкретно дашборд использовать для мониторинга (Grafana + Prometheus или встроенные средства MLflow)?
Ответ: Grafana + Prometheus для технических метрик сервиса (latency, error rate) — это отраслевой стандарт. MLflow остаётся для трекинга экспериментов и метрик качества моделей, он не предназначен для онлайн-мониторинга сервиса.
